# Architecture Overview

## Style: modular monolith + worker, not microservices (yet)

Brief §155/§156 is explicit: no premature microservices. CiM ships as:

- **`apps/web`** — Next.js app (public site + authenticated app + internal
  API routes). Owns request/response, auth, and thin API handlers only.
- **`apps/worker`** — Node/TypeScript worker process(es) consuming a Redis
  queue (BullMQ) for everything long-running: crawling, parsing, dedup,
  embeddings, classification, alert evaluation, digest/report generation.
- **`packages/*`** — shared, framework-agnostic domain code (see Monorepo
  layout) imported by both apps. This is where domain boundaries actually
  live, so that pulling a package out into its own service later (search,
  ingestion, AI, analytics — per §155) is a deployment change, not a
  rewrite.

The web app never talks to source content over the network directly for
ingestion, and never performs expensive AI synthesis inline in a request —
those are always queued jobs (§34, §91, §128).

## Request flow (target end-to-end, brief §156)

```
PUBLIC WEB → AUTH → ORGANIZATION → WORKSPACE → PROJECT → MONITORING
  → INGESTION LAYER → NORMALIZATION → DEDUPLICATION → SEARCH INDEX
  → AI ENRICHMENT → ANALYTICS → ALERT ENGINE → NOTIFICATION ENGINE
  → REPORT ENGINE → DASHBOARD / EMAIL / API
```

Concretely:

1. **Web** authenticates the request, resolves `organization_id` from the
   **session**, never from client-supplied input (ADR-001).
2. **MonitoringQuery** rows describe what to watch; a scheduler
   (`apps/worker` cron jobs) enqueues `crawl_source` jobs per active
   `Source` on its polling interval.
3. Each connector fetches → the shared ingestion pipeline (`packages/
   ingestion`) validates, parses, normalizes into the canonical `Article`
   shape, deduplicates, detects language, extracts entities, matches
   against active `MonitoringQuery` rules to produce `Mention` rows.
4. Mentions are indexed for search (`packages/search` abstraction) and
   aggregated into `MetricSnapshot`/daily aggregates (`packages/core`
   analytics).
5. The alert engine evaluates rules against new mentions/aggregates,
   producing deduplicated `AlertEvent`s → `Notification`s (in-app/email).
6. AI enrichment (`packages/ai`) runs as a cost-tiered pipeline (cheap
   classification → relevance/dedupe support → topic → expensive synthesis
   only for what surfaces to a user) and always stores evidence alongside
   any generated insight.
7. Reports/digests are generated by scheduled or on-demand worker jobs and
   delivered via the email abstraction or read from the dashboard/API.

## Monorepo layout

```
apps/
  web/            Next.js app (public site, authenticated app, API routes)
  worker/         Queue consumers + scheduled jobs
packages/
  ui/             Design-system components (shadcn/ui-based), tokens
  db/             Drizzle schema, migrations, repositories, seed data
  core/           Domain logic: tenancy, RBAC, scoring, aggregation, dedupe
  search/         Search abstraction (Postgres FTS today, pluggable)
  ingestion/      SourceConnector interface + implementations + pipeline
  ai/             AIProvider interface + prompt/schema layer + trust layer
  config/         Shared env/config loading & validation
  validation/     Shared Zod schemas used by web + worker boundaries
docker/           docker-compose service definitions
migrations/       (re-exported from packages/db for tooling convenience)
scripts/          One-off/dev scripts
docs/             This documentation tree
```

No package is created until a second real consumer needs it — e.g.
`packages/search` exists from day one because both `apps/web` (query) and
`apps/worker` (index writes) need the same abstraction; a hypothetical
`packages/email-templates` is not created until there's more than one
place rendering emails.

## Tenancy boundary

See ADR-001. Every domain query in `packages/core`/`packages/db` that
touches tenant-scoped tables takes an explicit, non-optional
`organizationId` argument sourced from the authenticated session — there is
no "global" query helper that can accidentally skip scoping.

## Why not microservices now

Splitting search/ingestion/AI/analytics into separate deployables today
would add operational complexity (deployment, networking, observability)
without a scaling problem that justifies it. The package boundaries above
are chosen so that when/if scale demands it, each package can be extracted
behind the same interface it already exposes internally, with its callers
unchanged beyond a transport shim.

## Fault isolation (brief §93)

- One source failing does not block others (per-source job, own backoff).
- AI provider outage does not stop ingestion — AI enrichment is applied
  asynchronously and mentions exist without it (`ai_status: pending/
  failed`); the UI shows mentions with AI fields "Not available" rather
  than blocking.
- Search index corruption does not lose data — Postgres is the system of
  record; the search index is rebuildable from it (ADR-002).
- Worker crash does not lose jobs — BullMQ persists jobs in Redis with
  retry/backoff and a dead-letter queue for exhausted retries.
